### **Функциональные требования**

Интернет-банк формирует код и направляет его клиенту, используя СМС-шлюз, и ожидает подтверждения операции от клиента. <br/> 4. Клиент вводит полученный СМС-код. <br/> 5. Интернет-банк формирует заявку на открытие депозита и передает ее в АБС. |
| UC6 | Сотрудник отдела депозитных продуктов (бэк-офис), АБС, СМС-шлюз | Обработка заявки на открытие депозита  | 1. Сотрудник отдела депозитных продуктов видит заявку в АБС. <br/> 2. Сотрудник подтверждает условия депозита в АБС. <br/> 3. АБС открывает депозит для клиента, осуществив перевод указанной в заявке суммы с нужного счета клиента. <br/> 4. АБС формирует уведомление для клиента и направляет его в СМС-шлюз. |

### **Нефункциональные требования**

|**№**|**Требование**|
| :-: | :- |
| R   | **Надёжность (Reliability)** |
| R1  | Сервисы должны работать 24/7 |
| R2  | SLA 99,9% |
| P   | **Производительность (Performance)** ||
| P1  | Отклик по всем операциям в интерфейсах должен быть максимально быстрым и занимать миллисекунды |
| P2  | Возможность горизонтального масштабирования интернет-банка |
| +R  | **+ Ограничения (Restrictions)** ||
| +R1 | Шифрование трафика при передаче с сайта и интернет-банка ||
| +R2 | Доработки функционала СМС лучше делать без привлечения подрядчика: можно сделать силами команды разработки банка ||
| +R3 | Предпочтительно использовать существующие технологии: PHP, React.js, C#, ASP.NET, Delphi, MS SQL, Oracle. Новые технологии должны быть совместимы с существующими. В качестве очередей сообщений предпочтительно использовать Kafka ||
| +R4 | Текущая версия платформы интернет-банка не совместима с очередями сообщений Kafka. Но можно рассмотреть переход на микросервисную архитектуру (в MVP только в части задачи открытия депозитов) ||
| +R5 | Справочные данные, загружаемые при проведении платежей, не обеспечивают требуемое время отклика (грузятся больше секунды) ||
| +R6 | Требуется избегать прямой работы интернет-банка с API АБС (из-за перегруженности базы данных) ||
| +R7 | АБС может масштабироваться только вертикально из-за своей базы данных ||

### **Решение**

Диаграммы контекста и контейнеров выполнены в draw.io: [C4-Diagrams.drawio](./C4-Diagrams.drawio)

Управление депозитами выделяется в отдельный сервис, разрабатываемый на ASP.NET Core и использующий базу данных MS SQL. Сервис будет предоставлять HTTP API для работы с заявками по депозитам и предоставляющий информацию об актуальных и персональных ставках по депозитам.

Общение между компонентами системы будет производиться с использованием очередей сообщений на базе Apache Kafka. Это потребует переписать такие компоненты системы как десктопный клиент АБС, СМС-шлюз и систему кол-центра - потребуется подписка и публикация сообщений в очереди.

### **Альтернативы**

Сервис депозитов можно сделать частью АБС. И в целом начать перепроектировать АБС стараясь уйти от сложной бизнес-логике на запросах PL-SQL в Oracle. 

**Недостатки, ограничения, риски**

Внедрение очередей сообщений на базе Kafka хоть и перспективное, но может потребовать больших усилий многих команд разработки. Настройка Kafka также требует практических умений, возможно потребуется нанять DevOps-инженера.
